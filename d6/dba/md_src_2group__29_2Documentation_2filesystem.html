Tiny Persistent Filesystem – Implementation Summary

Goal

The objective was to implement the smallest possible persistent storage system for the OS. The system should reliably:

  • write data to disk
  • survive a reboot
  • read the same data back

This demonstrates real persistence, not just in-memory storage.

Design Overview

The system is structured as a simple stack:

Shell commands
→ Tiny filesystem
→ ATA PIO disk driver
→ QEMU disk image (fs.img)

Each layer has a clear responsibility:

  • Shell: user interaction (write, cat, ls, format)
  • Filesystem: manages files and metadata
  • ATA layer: reads/writes raw disk sectors
  • Disk image: provides persistent storage across reboots

Why a Separate Disk

A second QEMU disk (fs.img) was used instead of the boot image:

  • avoids mixing kernel and user data
  • prevents data loss when rebuilding the OS
  • mimics real systems (separate boot + storage devices)

Why ATA PIO

ATA PIO was chosen because it is the simplest realistic block I/O method:

  • direct port I/O (no DMA or interrupts)
  • minimal implementation complexity
  • still models real hardware behavior

Key “Magic Bits” (Hardware Control)

Some constants are essential to make the disk work:

  • I/O ports

&#x20; * 0x1F0 → primary ATA data port

&#x20; * 0x3F6 → control port

  • Status register bits

&#x20; * 0x80 (BSY) → device busy

&#x20; * 0x08 (DRQ) → ready to transfer data

&#x20; * 0x01 (ERR) → error

These are used to correctly synchronize with the disk:

  • wait until not busy
  • ensure data is ready before reading/writing
  • Commands

&#x20; * 0x20 → read sector

&#x20; * 0x30 → write sector

&#x20; * 0xE7 → flush cache

  • Drive select (0xF0)

&#x20; * enables LBA mode

&#x20; * selects the secondary disk (slave)

&#x20; * includes top bits of the sector address

These values are not arbitrary—they come directly from the ATA specification and are required for correct hardware communication.

Filesystem Design

Why a Flat, Fixed Layout

The filesystem was intentionally designed to be:

  • flat (no directories)
  • fixed-size metadata
  • append-only allocation

This keeps the implementation:

  • small
  • predictable
  • easy to debug and explain

On-Disk Layout

Sector 0 → Superblock
Sector 1–4 → File table
Sector 5+ → File data

Superblock

Contains global metadata:

  • magic number (filesystem identity)
  • version
  • layout information
  • next_free_sector (allocation pointer)

Magic number: 0x53465954

Used to verify the disk is correctly formatted.

File Table

  • Fixed-size entries (32 bytes each)
  • Total: 64 files

Each entry stores:

  • filename (16 bytes)
  • start sector
  • file size
  • used flag

The fixed size makes indexing simple and avoids complex parsing.

Data Area

Stores file contents as contiguous sectors.

Allocation Strategy

The filesystem uses a simple append-only approach:

  • new files are written at next_free_sector
  • pointer is incremented after each write
  • overwritten files allocate new space (old data is not reused)

Why this design?

Avoids implementing:

  • free space tracking
  • fragmentation handling
  • compaction

Tradeoff: wastes space, but greatly simplifies the system.

File Operations

Write

High-level steps:

  1. Find existing or free file entry
  2. Calculate required sectors
  3. Write data sequentially to disk
  4. Update file metadata
  5. advance next_free_sector

Important detail:

  • Data is written in 512-byte sectors
  • Partial sectors are zero-padded to avoid garbage data

Read

  1. Locate file entry
  2. Read required sectors
  3. Copy only valid bytes
  4. return a null-terminated buffer

Persistence Validation

Persistence was verified using this workflow:

  1. Boot OS
  2. Format disk
  3. Write file
  4. Reboot QEMU
  5. Read file back

Successful read after reboot confirms true disk persistence.

Key Design Decisions

The most important choices were:

  • using a separate persistent disk
  • building on raw sector I/O
  • designing a minimal fixed-layout filesystem
  • using append-only allocation
  • validating data with a magic number + version

Limitations (Intentional)

The system deliberately omits:

  • file deletion
  • space reuse
  • directories
  • permissions
  • crash recovery
  • fragmentation handling

These were excluded to prioritize correctness and simplicity over completeness.

Future Work

Possible improvements:

  • file deletion (rm)
  • free-space reuse
  • directory structure
  • better error handling
  • crash-safe writes (journaling)

Key Takeaway

The system proves that:

‍A minimal OS can achieve real persistence using only raw sector I/O, a small metadata structure, and a simple allocation strategy.

All constants and “magic values” in the system are either:

  • required by ATA hardware, or
  • carefully chosen to create a clean, fixed, and explainable disk layout
